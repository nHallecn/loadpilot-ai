# Priority 1 — Controlled Bottleneck Investigation

## Why this exists

The original LoadPilot comparison changes **two** properties at once: 80ms serialized work (slow) vs 8ms concurrent work (optimized). Even when p95 improves substantially, the original pair cannot tell which intervention contributed to that difference.

This milestone introduces a third variant and two one-factor contrasts. **Each contrast changes one declared property while holding the other constant.** The experiment is still a private, synthetic, in-process Fastify benchmark—not proof of production root cause.

## Three variants and causal hypotheses

| Variant | Scheduling | Simulated work per request |
| --- | --- | --- |
| `slow` | Serialized queue | 80 ms |
| `parallel_slow` (new) | Independent parallel handlers | 80 ms |
| `optimized` | Independent parallel handlers | 8 ms |

**Contrast A — serialization hypothesis:** `slow` → `parallel_slow`, both at 80ms simulated work. Changes only the execution scheduling mechanism.

**Contrast B — processing-duration hypothesis:** `parallel_slow` → `optimized`, both with independent concurrent work. Changes only the simulated work time (80ms → 8ms).

The three experiments must use identical scenario, concurrency, planned duration, request start rate, and metric focus. They run in explicit sequence; results are measured rather than generated by AI. Changing one configured factor at a time is an improvement over the old mixed comparison, but single ordered trials remain vulnerable to drift and workload effects.

## Product flow

Open the dashboard and click **Isolate bottleneck factors** (no Meta model credits). The UI executes three bounded experiments sequentially, then calls a read-only deterministic assessment endpoint. It shows measured p95 latency for both contrasts, the exact factor changed, the properties held constant, and an evidence classification.

Each measured run still obeys the existing demo limits: 1–20 concurrency, 5–30 seconds, 1–50 request starts/sec and a hard maximum of 500 requests. Only bundled `demo-api` is permitted. Cancellation terminates new starts, not in-flight handlers.

## Endpoint and contracts

`POST /investigations/controlled`, with `Authorization: Bearer <LOADPILOT_DEMO_TOKEN>`:

    {
      "serializedRunId": "<UUID for slow>",
      "parallelSameWorkRunId": "<UUID for parallel_slow>",
      "parallelFastWorkRunId": "<UUID for optimized>"
    }

Accepts **three distinct, completed, chronologically ordered** records with identical configurations, at least 10 completed request samples each and valid metrics. Unknown IDs → HTTP 404, malformed input → HTTP 400, incompatible records → HTTP 422, unauthorized → HTTP 401. The read-only endpoint never calls the Meta API and never runs workloads.

### Predeclared interpretation threshold

A contrast's measured signal is recorded as `observed_at_demo_threshold` if p95 decreased by at least **10 ms and 20%** without any increase in observed error rate. Otherwise the outcome is `not_observed_at_demo_threshold` or `error_regression`.

Both signals → `both_signals_observed`; only one → `serialization_signal_only` or `processing_delay_signal_only`; neither → `neither_signal_observed`; an error-rate regression → `inconclusive_error_regression`.

These are **descriptive threshold labels**, not confidence levels, statistically significant findings, or confirmed production causes. A non-observed signal does not disprove a hypothesis.

The report returns `sourceRuns`, two explicit `contrasts`, a deterministic `conclusion`, and an integrity checksum of the report content before the `integrity` field. It is possible to recalculate the SHA-256 hash from the underlying report data. As with earlier evidence export, this checksum is **not a digital signature**.

## CLI demo

With the API running from `apps/api`, execute:

    node --env-file=.env scripts/controlled-investigation.mjs

Three bounded sample runs and a read-only assessment occur. A JSON report is stored in `apps/api/reports/`, which is gitignored. Neither the CLI nor the dashboard isolation button spends Meta credits.

## Acceptance criteria

- Two contrasts change **exactly one declared factor each** using a common parallel 80ms control.
- All results come from actually completed request measurements.
- Incompatible variant order, missing runs, repeated IDs, insufficient samples and mismatched plans are rejected.
- The classification distinguishes evidence for both, one, neither, and error-regression cases.
- The UI exposes the changed factor, held constants, observed values, and uncertainty.
- The API is read-only, authenticated and has no configurable network target.
- All tests and build checks pass; the live private Codespaces workflow still needs a manual run before recording.
